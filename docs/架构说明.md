# 大帅拼音输入法 · 架构说明

> 你每敲一个键，到屏幕上出现"大帅拼音输入法"这六个字，中间发生了什么。

## 一、五层结构总览

```
┌─────────────────────────────────────────────────────────────┐
│ ① Windows TSF（系统输入框架，微软的）                          │
│    ctfmon.exe / msctf.dll —— 把输入法 DLL 加载进每个应用进程    │
└───────────────┬─────────────────────────────────────────────┘
                │ COM 接口调用
┌───────────────▼─────────────────────────────────────────────┐
│ ② 前端 TIP：weasel.dll (32位) / weaselx64.dll (64位)          │
│    极薄的"传令兵"：收按键、把结果写回应用，自己不做任何计算      │
└───────────────┬─────────────────────────────────────────────┘
                │ 命名管道 IPC（跨进程通信）
┌───────────────▼─────────────────────────────────────────────┐
│ ③ 服务进程：WeaselServer.exe（任务栏托盘图标就是它）           │
│    全机唯一实例；托管引擎；用 Direct2D 画候选词窗口             │
└───────────────┬─────────────────────────────────────────────┘
                │ C API（rime_api.h，进程内调用）
┌───────────────▼─────────────────────────────────────────────┐
│ ④ 引擎：rime.dll（librime，BSD 协议）                         │
│    拼音切分 → 查词典 → 组句解码；内嵌三个插件：                 │
│    lua（脚本扩展）/ octagram（语言模型）/ predict（预测）       │
└───────────────┬─────────────────────────────────────────────┘
                │ 读文件（%APPDATA%\Rime）
┌───────────────▼─────────────────────────────────────────────┐
│ ⑤ 数据层（万象拼音，CC-BY-4.0）                               │
│    wanxiang.schema.yaml   方案：拼音规则、处理流水线定义        │
│    build\*.table.bin      编译后的词典（主词库 77.8MB）         │
│    wanxiang-lts-zh-hans.gram  语言模型 400MB（整句质量的来源）  │
│    *.userdb\              你的个人词典（本地自学习，LevelDB）   │
└─────────────────────────────────────────────────────────────┘
```

一句话版本：**微软的 TSF 负责"接线"，weasel 前端负责"传话"，WeaselServer 负责"画界面"，librime 负责"想"，万象数据负责"知识"。**

## 二、一次按键的完整旅程

以你在微信里打 `dashuai` 然后按空格为例：

1. 微信进程里的 **weasel*.dll**（TSF 已提前注入）截获按键 `d`；
2. 它通过**命名管道**把键码发给 **WeaselServer**（你的按键不出本机，管道是进程间通信，不是网络）；
3. WeaselServer 调 **rime.dll** 的 C API 处理按键；
4. librime 内部流水线开始工作：
   - **speller** 把 `dashuai` 切分成音节 `da shuai`；
   - **script_translator** 拿音节查 `build\wanxiang.table.bin`（词典），得到所有可能的词组合；
   - **octagram 插件**查 `.gram` 语言模型给每种组合打分（"大帅"和"打衰"哪个更像人话），动态规划选出最优整句；
   - **simplifier/filters** 做繁简转换、emoji、去重等后处理；
5. 候选列表原路返回，WeaselServer 用 Direct2D 在光标旁**画出候选窗**（候选窗是 Server 画的，不属于微信）；
6. 你按空格确认，weasel*.dll 通过 TSF 的编辑会话接口把"大帅"**写进微信的文本框**；
7. librime 同时把这次选择记进 `*.userdb`（个人词典），下次"dashuai"排序更靠前——这就是本地自学习，零云端。

## 三、"部署"是怎么回事

Rime 系输入法有个独特概念叫**部署（deploy）**：把人类可读的 YAML/文本词库**编译**成内存映射的二进制：

```
wanxiang.dict.yaml + dicts/*.yaml   ──┐
wanxiang.schema.yaml                  ├─→ 部署器 ─→ build\wanxiang.table.bin (词典树)
default.yaml / weasel.yaml            │            build\wanxiang.prism.bin (拼写索引)
*.custom.yaml (你的自定义补丁)         ┘            build\*.schema.yaml (合并后配置)
```

- 平时打字**只读 build\ 里的二进制**，所以启动快、查询快（内存映射，不用全加载）；
- 改了任何 YAML 配置后需要**重新部署**（托盘图标右键 → 重新部署）；
- `.gram` 语言模型**不参与编译**，运行时由 octagram 直接内存映射加载。

我们踩过的坑：librime 靠**文件修改时间**判断要不要重新编译，`Expand-Archive` 解压会保留 zip 里的旧时间戳，导致部署被静默跳过——所以 `install.ps1` 解压后统一刷新时间戳，并绕过不可靠的 `WeaselDeployer.exe`，直接 P/Invoke 调 rime.dll 的部署 API。

## 四、每一层是"谁的"、什么协议、我们改了什么

| 层 | 项目/所有者 | 协议 | 我们的定制 |
|---|---|---|---|
| ① TSF | Windows 自带 | — | 无（也无法改） |
| ② 前端 TIP | rime/weasel | GPL-3.0 | 注册表显示名 小狼毫→大帅拼音 |
| ③ 服务进程 | rime/weasel | GPL-3.0 | 暂无（托盘提示仍显示"小狼毫"，改它需 fork 重编译） |
| ④ 引擎 | rime/librime | BSD-3 | 无需改，插件已齐 |
| ⑤ 方案+词库 | amzxyz/rime-wanxiang | CC-BY-4.0 | 原样使用，`rime-config/` 预留自定义补丁位 |
| ⑤ 语言模型 | amzxyz/RIME-LMDG | CC-BY-4.0 | 原样使用 |
| 整合层 | **本仓库（大帅拼音）** | GPL-3.0 | install/uninstall 脚本、品牌化、文档 |

**品牌名出现的三个位置**：
1. 语言栏/输入法切换列表 —— 注册表 Description ✅ 已改为"大帅拼音"
2. 托盘图标提示、右键菜单、部署通知 —— 编译在 WeaselServer.exe/weasel.dll 资源里 ⏳ 需 fork weasel 重编译（阶段 1.5）
3. 候选词窗口 —— 本来就不显示名字，无需改

## 五、为什么阶段二要自研前端

现在的依赖链里 ②③ 层是 GPL 的 weasel，界面文案、托盘行为、设置方式都不归我们控制。阶段二用 MIT 协议的微软 SampleIME 做骨架自研 ②③ 层，librime 引擎放独立服务进程（把 GPL 的 octagram 隔离在进程边界外），就能：
- 彻底的"大帅拼音"品牌（不再借小狼毫的壳）；
- 自己的 GUI 设置面板（Rime 生态最大短板：改配置要手写 YAML）；
- 协议链干净（BSD+MIT+CC-BY），保留闭源/商用选项。
